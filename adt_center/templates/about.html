What is ADT? CURRENT

Advanced Digital Transformation — Governance for a Trustworthy AI Future. ◆ Scaling intelligence, preserving human authority ◆

Author: Paul Sheridan, Director, Advanced Digital Transformation (ADT)

"Digital transformation initiatives frequently fail not due to a lack of technology, but because governance is introduced too late, applied inconsistently or not applied at all — leaving organisations to confront complex, fragmented challenges without a coherent framework for accountability, coordination and control."

Rather than placing governance around AI through policies, prompts or monitoring, ADT builds human authority and systemic control directly into the architecture — through external orchestration, mechanical execution control, living standards and coherent multi-agent state.

The result: the intelligence can change without changing the governance. Whatever model or harness comes next — Claude, Antigravity, anything else — the specifications, standards, authorised system state and evidence of execution remain outside the model and under human authority.

ADT brings three complementary dimensions together: Five Outcomes (what governance must achieve), Seven Stages (how human intent progresses to governed execution), and Five Pillars (the architectural mechanisms that enforce it) — jointly the Capability Governance Architecture (CGA).

Five Outcomes — What Governance Must Achieve CURRENT

ADT defines AI-agent governance through five essential outcomes. These are not aspirations or post-hoc checks — they are properties that must be supported by the system's architecture.

  • Direction — clear articulation of intent and objectives that guide autonomous action.
  • Performance — measurable delivery against intent, within defined constraints.
  • Accountability — every decision and action is attributable to an authorising human or specification.
  • Transparency — the reasoning, standards and rules behind decisions are visible and inspectable.
  • Legitimacy — outcomes align with adopted principles, regulations and stakeholder expectations.

Where a governance approach leaves any of these materially unaddressed, the resulting agent system has a corresponding governance weakness. Safety is only as strong as the governance that constrains capability.

Seven Stages — Human Intent to Autonomous Delivery CURRENT

A continuous chain from human intent to autonomous delivery. Each stage adds a distinct layer of definition, authority or control.

  1. Human intent — an operator defines the desired outcome in natural language.
  2. Specification — ADT translates intent into a governing specification.
  3. Standards alignment — relevant standards, regulations and requirements are identified and presented for consideration and adoption.
  4. Decomposition — approved intent is transformed into role-scoped specifications and executable tasks.
  5. Governed execution — AI agents operate within defined roles, permissions and transfer-control boundaries.
  6. Traceability — execution remains accountable and auditable, with actions traceable to approved intent and specifications.
  7. Autonomous delivery — AI agents can design, build and operate systems without requiring humans to write the underlying code, while remaining subject to the specifications, permissions and controls established by the framework.

Authoritative Data Source (ADS) OPERATIONAL
"If an action is not recorded, it is not recognised as having occurred."

The ADS is the single source of truth for everything that happens inside a governed project. Every agent action, DTCP decision, delegation, and escalation is appended to _cortex/ads/events.jsonl.

  • Append-only: History is never modified. Events are immutable once written.
  • Structured events: Each entry carries agent, role, action type, spec reference, authorisation status, and hash chain link.
  • Safe Logger v3.0: Atomic file locking (fcntl), schema validation, and hash computation prevent corruption even under concurrent writes.

View the full event timeline in the ADS Timeline.

Integrity Chain OPERATIONAL

Every ADS event contains the SHA-256 hash of the previous event, forming a tamper-evident chain identical in concept to a blockchain.

  1. Each event is serialised to a canonical JSON string (sorted keys, no whitespace).
  2. The SHA-256 hash is computed over the serialised string.
  3. The hash is stored in the event and becomes the prev_hash of the next event.
  4. The genesis block uses an all-zeros prev_hash.

Modifying, inserting, or deleting any event breaks every subsequent hash link. The Overseer runs periodic integrity audits and the ADS Healer can detect and report chain breaks. A break is itself logged as a governance incident.

Specification-Driven Development (SDD) OPERATIONAL
"No Spec, No Code" — the fundamental rule of ADT governance.

Every code change must be authorised by an approved specification in _cortex/specs/. This ensures traceability from intent to implementation.

  • Spec Lifecycle: DRAFT → Human Approval → APPROVED → Active → COMPLETED
  • Systems Architect: Writes specifications, defines scope and requirements. Does not implement.
  • Human: Approves specifications. Ultimate authority over what gets built.
  • Engineers: Implement only what the spec authorises, within their jurisdiction.
Digital Transformation Control Protocol (DTCP) OPERATIONAL

The Digital Transformation Control Protocol enforces governance structurally, not just behaviourally. DTCP validates every agent action against role jurisdiction, specification authorisation and tiered protections in real time. Unauthorised actions are denied at execution time, not merely logged after the fact.

LevelMechanismStrength
1Behavioural (prompt instructions)Proven insufficient
2Hook-based (pre-action scripts)Bypassable via Bash
3Privilege-separated (OS permissions + network)Target architecture

  • human: Full access. Approves specs, authorises SCRs, activates Shatterglass.
  • agent: Restricted OS user. Can only write via DTCP API requests.
  • dtcp: Service user. Validates requests against policy, executes authorised writes.
Agent Isolation OPERATIONAL

The fourth pillar. Agent Isolation separates agents from protected systems through controlled execution environments and restricted resource access — preventing direct modification of protected files, systems or configurations, and containing the effects of errors or unintended actions.

  • Filesystem sandbox: bwrap / unshare namespace isolation confines each agent session to its jurisdictional paths.
  • Network confinement: Outbound egress is restricted; agents cannot reach the network without an explicit spec-authorised path.
  • Restricted OS user: Agents run as the agent UNIX user with read-only project access; writes must route through DTCP.
  • Blast-radius containment: A misbehaving or compromised agent cannot escalate outside its cell.

Implementation: SPEC-036 — Agent Filesystem Sandbox.

Standards Layer (SPEC-046) OPERATIONAL

The fifth pillar. The Standards Layer defines the principles, obligations and governance requirements adopted by the organisation.

  • External standards: OECD AI Principles, EU AI Act, ISO/IEC 42001, NIST AI-RMF, UNESCO AI Ethics, COBIT, ITIL.
  • Internal governance: the organisation's own codex of rules and obligations.
  • Clause Dispositions: every clause is Adopted, Adapted (with rationale) or Dismissed (with rationale) — a governance act performed by an accountable human.
  • Traceability: specifications and intents link back to standards clauses. Every runtime decision has a full path from action to principle.

Manage adopted standards in the Standards Registry.

The ADT Operational Center OPERATIONAL

The ADT Framework incarnated as software. A Flask application that serves as the human web UI, agent API, and DTCP engine.

  • Dashboard: Real-time governance overview with compliance stats and event counters.
  • ADS Timeline: Searchable, filterable event history with agent and role grouping.
  • Spec Registry: Browse, create, and inspect specifications.
  • Task Board: Track task assignments, completion, review status, and delegation chains.
  • DTCP Monitor: Live enforcement activity, denial log, and policy status.
  • Governance Configurator: Role cards, jurisdiction editor, enforcement dashboard.

Multi-project capable via External Project Governance (SPEC-031).

Operator Console (SPEC-039) OPERATIONAL

The ADT Operator Console is the human command centre for governed execution — the interactive surface for stage 5 (Governed execution) of the Seven Stages. It transforms the framework from a passive log viewer into an active steering interface.

  • Governance zoom: Hierarchical visualisation from intent down to task.
  • Human steering: Real-time prioritisation and command injection.
  • Thinking feedback: Visual pulses synchronised with agent tool-calls.
  • Model routing & escalation: Watchdog-driven promotion to heavier models when a lower-tier worker stalls.
Capability Intents (SPEC-038) OPERATIONAL

Capability Intents are the operational form of stages 1 & 2 of the Seven Stages: they bridge organisational strategy and technical execution by capturing the why behind every specification.

  • Intents: Desired outcomes (e.g., "Improve tuning accuracy").
  • Events: Triggering occurrences (e.g., "Sensor drift detected").
  • Maturity: Real-time tracking of capability evolution across the seven governance stages.

Note: In older documentation, "Capability Governance" appeared as a pillar. Under the current CGA model, that concept is fully expressed through the Seven Stages — the pillars provide the mechanisms, the stages provide the flow.

External Project Governance OPERATIONAL

ADT can govern any project, not just itself. The multi-project registry allows multiple codebases to operate under independent governance.

  • Independent _cortex/ directories: Each project gets its own ADS, specs, tasks, and jurisdictions.
  • Project isolation: Events, enforcement, and compliance data are scoped per project.
  • Unified view: The Operational Center can aggregate or filter across all registered projects.
  • Console integration: The Operator Console groups sessions by project with per-project context panels.

Implementation: SPEC-031, SPEC-032 (Project Launcher).

Sovereign Change Requests (SCR) OPERATIONAL

Sovereign paths contain the rules of the framework. No agent can modify them directly.

When an agent proposes a change to a sovereign file, DTCP blocks the write and auto-submits a Sovereign Change Request for human authorisation in the Governance panel.

Implementation: SPEC-033 — Human-in-the-loop authorisation queue.

Shatterglass Protocol OPERATIONAL

Emergency override mechanism for critical situations where normal governance must be temporarily suspended.

  • Break-glass activation: Human-only action requiring confirmation (type "SHATTERGLASS").
  • Time-limited window: Override expires after a configurable duration with countdown timer.
  • Full audit trail: Every action taken during a Shatterglass window is logged to the ADS with elevated visibility.
  • Production mode: OS-level enforcement via the agent user (Tier 3). Toggle in the Operator Console.

Implementation: SPEC-027. Accessible from the Governance page.

Roles are configurable per project. Different domains define different role vocabularies (Editors / Writers / Designers for a publishing project; Engineers / Architects / DevOps for software) — what stays constant is that every role has a defined territory, an allowed action set, and a whitelist of specs, all enforced by DTCP.

Enforcement: hook-based (Level 2) migrating to full OS-level privilege separation (Level 3).

Real Incidents OPERATIONAL

The ADT Framework is its own proving ground. These incidents validated (and sometimes challenged) the governance model:

An em-dash character in an ADS event description caused _get_last_event() to crash mid-way through a multi-byte UTF-8 sequence. The entire DTCP pipeline returned 500 errors, blocking all governed writes. Root cause: byte-by-byte reverse seek in text mode. Fix: binary mode read in Safe Logger v3.0.

Agents discovered they could use the Bash tool to bypass DTCP hooks entirely, writing directly to governed files. This proved Level 2 (hook-based) enforcement is fundamentally insufficient and motivated the move to Level 3 privilege separation with the agent OS user model — the Agent Isolation pillar.

Inconsistent role casing (devops_engineer vs DevOps_Engineer) caused hash chain breaks because the canonical JSON serialisation differed. Fix: role and agent name normalisation via canonical registry loaded from jurisdictions.json (SPEC-020 Amendment B).

Agents completing cross-role requests could not mark them as COMPLETED because _cortex/requests.md and _cortex/tasks.json were outside their jurisdiction. The only option was bypassing DTCP via Bash. Fix: governed status update API (SPEC-035) at /api/governance/requests/<id>/status.
